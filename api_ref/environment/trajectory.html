Trajectory#

class Trajectory(ref_frame=None, origin=None, body=None, degree_poly: int = 3, parameters=None, offset=None, STMs=None, STMs_timestamp=None, propagator_settings_dict=None, state_array=None, leg_array=None, mass_profile=None, use_saved_stms: bool = False, max_interp_error: float | None = 0.001, per_body_spk: bool = False)#

Bases: object

Represents a spacecraft or celestial object’s trajectory in a defined reference frame and origin.

This class encapsulates trajectory data, including position, velocity, estimated parameters, and state transition matrices (STMs). It supports both single-phase trajectories and multi-leg mission sequences.

The trajectory stores the discrete time history \(\{(t_i,\,\mathbf{r}_i,\,\dot{\mathbf{r}}_i)\}_{i=0}^{N}\) and writes it into a SPICE SPK kernel so that the state at any epoch \(t \in [t_0, t_N]\) can be retrieved via Hermite interpolation, which constrains the position curve with the sampled velocities:

\[\mathbf{r}(t) \approx \sum_{k=0}^{d} c_k\,t^k, \qquad \mathbf{r}(t_i) = \mathbf{r}_i, \quad \dot{\mathbf{r}}(t_i) = \dot{\mathbf{r}}_i\]

where \(d\) is degree_poly (default 3). The degree is always odd: each node supplies both a position and a velocity, so a window of \((d+1)/2\) nodes fixes all \(d+1\) coefficients.

The trajectory can be initialized using:

  • Explicit position, velocity, and epoch inputs.

  • A StateArray directly from a propagator.

Notes

  • If state_definition is provided, the trajectory follows a single continuous model.

  • If sequence_definition is used, the trajectory consists of multiple segments (e.g., before and after a maneuver).

  • The trajectory is stored in a SPICE kernel format for interpolation and retrieval.

Saving to disk — SPK and JSON sidecars

Calling write_to_spk() writes two kinds of files that always live next to each other:

  1. SPK binary (<name>.bsp) — the position/velocity time-series in SPICE type-13 (unequally spaced Hermite) format. State at any epoch inside the covered arc is retrieved via SPICE polynomial interpolation, with the stored velocities constraining the position curve so that the velocity SPICE returns is the exact derivative of the position it returns.

  2. JSON sidecars — plain-text files written alongside the .bsp with the same base name and the suffixes listed below. They carry metadata that cannot be embedded in a standard SPK segment:

    • <name>_parameters.json — time-history of estimated parameters (e.g. range biases, SRP coefficients, empirical accelerations), plus the full state definition that describes what each column represents.

    • <name>_STMs.json — state transition matrices and their timestamps (written only when STMs are attached via add_STMs()).

    • <name>_settings.json — serialised propagator_settings_dict (force model, integrator tolerances, etc.) so the trajectory can be reproduced.

    • <name>_mass_profile.json — polynomial coefficients of the spacecraft mass as a function of time (written only when a mass_profile is provided).

Each sidecar is optional: the file is created only when the corresponding data is not None. All four sidecars share the same path prefix as the .bsp so that loading the kernel and its associated metadata is unambiguous.

Examples

Standard Initialization:

import scarabaeus as scb

# Define epochs
epoch_start = scb.SpiceManager.jd2et(2461809.72995654)
epoch_end = scb.SpiceManager.jd2et(2461809.72995654 + 1)
epochs = scb.EpochArray(np.linspace(epoch_start, epoch_end, 100),sys="TDB")

# Define position and velocity
position = scb.ArrayWUnits(np.random.rand(100, 3), "km")
velocity = scb.ArrayWUnits(np.random.rand(100, 3), "km/s")

# Initialize trajectory
traj = scb.Trajectory(
    name="Test_Trajectory",
    position=position,
    velocity=velocity,
    epoch=epochs,
    ref_frame="J2000",
    origin="SUN",
    body=scb.CelestialBody.from_constants("EARTH")
)

# Retrieve state at a given epoch
state = traj.get_state(epochs[0])

>>> print("Position:", state["position"])
'Position: [0.123, 0.456, 0.789] [km]'

Alternative Initialization from a Propagator:

# Initialize trajectory using propagated StateArray
traj = scb.Trajectory("Orbiter_trajectory", state_array=propagated_state_array)

get_STM_sequence(epoch: float, idx: int = None, idx_leg: int = None, tol_time: float = 1e-09) → ndarray#

Retrieve/interpolate the STM at epoch for BOTH:

  • non-sequence: self._STMs is (N, n^2) and self._STMs_timestamp is (N,)

  • sequence: self._STMs is a list of arrays, one per leg (or per segment block)

Behavior (sequence):

  • if idx_leg is given: interpolate within that leg

  • else: auto-detect leg from self._legs[*]["epoch_leg"] if available, otherwise fall back to using global timestamps if provided.

Notes

  • Works with flat STMs stored as length n^2 vectors.

  • Uses linear interpolation in coefficient space.

  • Handles exact hits within tol_time.

  • Interpolated results are checked against max_interp_error, this trajectory’s relative tolerance.

write_to_spk(spk_path: str, stm_format: str = 'json', sidecar_format: str = 'json', append_if_exists: bool = True, write_stms: bool = True, per_body_spk: bool = None) → None#

Write the trajectory to disk as a SPICE SPK file plus JSON sidecars.

The .bsp file contains the position/velocity time-series (SPICE type-13 Hermite segments). See Notes section for information on additional data that cannot be embedded in an SPK.

Parameters:
spk_pathstr

Destination file path. Must end with .bsp.

stm_format{“json”, “pickle”}, optional

On-disk format for the STM sidecar. "json" (default) writes a human-readable _stms.json; "pickle" writes a compact binary _stms.pkl (lighter on disk for large STM histories). Either is read back transparently by get_STMs().

sidecar_format{“json”, “pickle”}, optional

On-disk format for the parameters / settings / mass-profile sidecars. "json" (default) writes *_parameters.json etc.; "pickle" writes *_parameters.pkl etc. (same content, binary). Read back transparently by the SpiceManager getters.

append_if_existsbool, optional
If the given spk_path already exists:

  • True: append the trajectory segment to that file.

  • False: delete the existing file and write a new one in its place.

Defaults to True.

write_stmsbool, optional

Whether to write the STM sidecar at all. It is by far the largest artifact a trajectory produces — one matrix per output epoch, growing with the square of the state size — so a run that only wants the state history can skip it entirely. Defaults to True. The STMs held in memory are unaffected; only the file is skipped, so anything reading them back later (use_saved_stms) needs it.

per_body_spkbool, optional

When the trajectory holds several bodies, write one SPK per body — mission_EARTH.bsp, mission_ORBITER.bsp — instead of a single file carrying one segment per body. Each file then owns its sidecars, which is what a downstream tool expecting one body per kernel wants. Defaults to per_body_spk, i.e. False: one file with a segment per body. Ignored for a single body.

Raises:
ValueError

If spk_path does not end with .bsp.

UserWarning

If this Trajectory already has an associated SPK at a different path.

Notes

The written SPK is furnished. SPICE resolves each epoch from the last-loaded kernel that covers it, so within its time span this file shadows any SPK loaded earlier for the same body (a reconstructed mission ephemeris, for instance). Unload it, or write it to a path you can unload, if those earlier kernels must stay in effect.

Additional data that cannot be embedded in an SPK segment is written as plain-text JSON files with the same base path:

  • <spk_path base>_parameters.json — estimated parameters and state definition (written when parameters is not None).

  • <spk_path base>_settings.json — propagator settings dictionary (written when propagator_settings_dict is not None).

  • <spk_path base>_mass_profile.json — spacecraft mass polynomial (written when a mass_profile was passed at construction time).

  • <spk_path base>_stms.json — state transition matrices (written when STMs are attached and write_stms is True).

Each sidecar is created only when the corresponding data is present. All files share the same directory and path prefix as the .bsp.

Examples

traj.write_to_spk("/output/mission.bsp")
# Produces: mission.bsp, mission_parameters.json,
#           mission_settings.json  (if propagator settings exist)

property max_interp_error: float | None#

Relative tolerance on linear interpolation of the STM.

Every get_STM / get_STM_sequence lookup that falls between two stored epochs interpolates, and rejects the result when the estimated relative error exceeds this value. The estimate is curvature-based and scales as \(dt^2\), so halving the STM grid step cuts it by four.

The default, 1e-3, admits a grid step of roughly a minute on a low Earth orbit. Raise it to accept a looser fit on a coarser grid, or set it to None to skip the check entirely.

Notes

This replaces an absolute threshold on the first difference alpha (1 - alpha) ||Phi_1 - Phi_0||, which measured \(\|\Phi\|\) rather than the interpolation error and so failed on a long arc at any grid step. Values carried over from that scheme are not comparable.

property offset: ArrayWUnits#

A fixed position offset for coordinate transformations.

property origin: str#

The origin of the trajectory.

property parameter_units: list | None#

Per-parameter units backing parameters, in column order.

A list of (name, dim, units), one entry per estimated parameter of the primary body. Parameters of one body need not share units — a spacecraft solving for a delta-v (km/s) and a maneuver-epoch correction (sec) is ordinary — and when they differ, parameters is deliberately unitless because no single label describes the stacked block. This is then the only faithful record, and it is what gets written to the parameters sidecar.

None for sequence trajectories, whose legs carry their own units, and for trajectories with no estimated parameters.

property parameters: list#

Additional estimated parameters associated with the trajectory. These parameters include mission-specific estimated values, such as:

  • Ground station range biases (e.g., clock offsets, tropospheric delays).

  • Additional environmental parameters (e.g., solar radiation pressure coefficients).

  • Model calibration parameters (e.g., empirical accelerations).

If no additional parameters exist, returns None.

property per_body_spk: bool#

Whether a multi-body trajectory is written as one SPK per body.

False (the default) writes a single .bsp carrying one segment per body — compact, and what SPICE is designed for. True writes mission_ORBITER.bsp, mission_EARTH.bsp and so on, each with its own sidecars, for a downstream tool that expects one body per kernel.

Either way the bodies’ parameter sidecars are kept apart: they are named per body whenever there is more than one, since every body writes _parameters.json and a shared name would leave only the last.

Ignored for a single-body trajectory, which always writes one file.

  • Their associated reference objects (e.g., spacecraft, ground stations).

When True, get_STMs() reads STMs from the saved _stms.json sidecar instead of the in-memory STMs list.
